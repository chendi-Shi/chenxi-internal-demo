# 数据工程与规模化备忘录

状态：未来工作，不属于当前 Demo 已完成能力。

## Capital IQ PDF 受控实验

候选数据源：用户提供的 `Capital IQ Data` 目录。当前仓库按项目边界不读取、不复制系统原始内容，因此尚未对其中 PDF 做内容检查、导入或结果声明。

计划实验口径：

- 选择三家公司，固定一个自然月。
- 纳入正文中出现相应公司名称的全部 Capital IQ 报告，不要求报告主题与所选公司强相关。
- 公司别名、曾用名、ticker、子公司名是否算命中，必须在运行前固化为版本化规则。
- 保存文件 hash、解析器版本、页数、文本长度、OCR 状态和导入时间；不把原文复制到本仓库。
- 建立正负样本：强相关、弱提及、仅免责声明/同业表格出现、OCR 误识别。
- 分别测量 ingest 成功率、解析耗时、检索召回、Top-k 精度、弱相关污染、fetch token 和引用页定位。
- 输出只保留允许共享的聚合指标、脱敏查询和文档 ID；真实正文与账号信息不进入 Git。

该实验应由拥有数据接入责任的上游 Retrieval Hub 在受控环境执行。本仓库只消费正式 API/MCP 输出做 Dashboard 与评测，不新增 PDF 解析器或影子索引。

## 数据工程重点问题

- “正文出现公司名”会扩大召回但引入大量弱相关结果，需要把 mention 与主题相关性作为独立标注维度。
- PDF 表格、页眉页脚和免责声明容易制造高频假命中，应记录命中位置与版面区域。
- 同名公司、缩写和 ticker 容易歧义，应建立带版本的实体词典和人工复核样本。
- OCR 文档需记录置信与失败页，避免把解析缺失误判为检索失败。
- 同一报告的修订版或多渠道副本应按内容 hash 和业务主键去重。

## 日增数百份时的后续选择

1. 用队列把发现、下载、解析、分块、索引拆成幂等阶段，并记录每阶段状态。
2. 以批次和 worker 并发控制吞吐，设置背压、重试上限和死信处理。
3. 建立索引版本与原子切换，保证重建期间查询仍使用完整版本。
4. 监控端到端新鲜度、队列深度、解析失败率、每文档成本和搜索 P95 延迟。
5. 在真实基线证明 FTS 召回不足后，再评估实体检索、混合检索或 ANN；不得在 Dashboard 添加客户端 reranker。
6. 为删除、权限变化与合规请求建立从原文到 chunk、索引、缓存和引用的传播机制。
7. 对长文优先提出 passage/range fetch 契约，避免把完整报告注入模型上下文。

## 开始条件

执行真实 PDF 实验前，需要明确三家公司、月份、别名规则、数据使用权限、可共享指标，以及上游受控导入环境。任何真实文档处理都不在当前仓库内直接进行。
