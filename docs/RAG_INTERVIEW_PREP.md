### 组件增益应如何讲

百分点（pp）是指标差值乘 100；不能与相对百分比混用。以下表格来自各自的固定样本，**不能跨数据集比较数值大小**。

| 对照 | 已观察结果 | 可辩护的解释 | 尚未验证的解释 |
|---|---|---|---|
| 历史真实库：normalized hybrid − lexical | nDCG@10 **−18.226 pp** | 这套覆盖与融合配置在该题集退化 | “混合检索必然无用” |
| 历史真实库：RRF − normalized hybrid | nDCG@10 **+4.242 pp**，Recall@10 **+20.000 pp** | 同一历史实验中，替换融合方式改善了这两个指标；MRR@10 仍下降约 0.958 pp | “RRF 全面优于所有基线”；它的总体 nDCG 仍低于 lexical |
| 历史真实库：rerank − RRF | 总体 nDCG@10 **−0.401 pp**；英文 **+6.395 pp**，中文 **−7.197 pp** | 总体均值掩盖了不同题组的方向差异，应检查模型、截断、候选和标注 | 把退化全归因于语言；中英题目的主题不同，尚未做受控语言对照 |
| 历史真实库：rewrite − rerank | nDCG@10 **+1.577 pp**；英文不变，中文 **+3.155 pp** | 该规则扩展路径的历史增量为正；只覆盖已选问题 | “LLM rewrite 提升了效果”；当前扩展是确定性规则 |
| 当前 SQLite：去掉 concept expansion / title guard | 两者 nDCG@5 差值均为 **0** | 当前小样本的相关性指标未暴露作用；title guard 关闭后 payload 仍发生变化 | “这两个组件可以删除” |
| 当前 SQLite：alpha 来源权重 ×10 | nDCG@5 **+2.31 pp**，W/T/L = **1/15/0** | 一个问题改善推动了均值；fixture 正例来源不均衡 | “整体检索提升 2.31%”“证明最优来源权重为 10” |
| 当前 SQLite：返回 top-3 相较 top-10 | nDCG@5 相同；平均详细响应约 **958.4 vs 1420.1 字节** | 这批短文中保留前三条即可覆盖相同的前五位相关性；响应体较小 | token 账单下降相同比例、长文场景也能维持答案质量 |

最有价值的追问是“**什么证据能推翻我的解释**”。例如怀疑 reranker 的语言适配，应在同一中文题集、同一候选、同一截断与池大小下比较重排模型，而不是拿另一组英文题的均值作证据。

### 此前三组结果的专题分析：长度与模型如何改变组件收益

本节固定选取此前已经核验的 E5-small/256、E5-small/512 和 multilingual MiniLM/256 三组，第四组完成不改变以下数值。三组具有相同 corpus、query 和运行指纹；每组都是 18 配置×300 同题一次观测。跨组对照先核对 query IDs 和固定配置，再按唯一 query 的差值做 2,000 次配对 bootstrap（seed=20261015，nearest-rank 百分位）。以下只选择已预设的 dense、RRF、RRF+rerank 对照；完整四配置的跨组结果在[报告 JSON](evaluation/PUBLIC_GPU_ABLATION.json)。

| 对照（候选 − 参考） | 固定检索配置 | nDCG@10 参考 → 候选 | Δ pp；95% CI pp | W/T/L |
|---|---|---|---|---|
| E5 512 − E5 256 | dense | 0.65495 → 0.67700 | +2.204；[+0.311, +4.128] | 52/218/30 |
| E5 512 − E5 256 | RRF | 0.68423 → 0.69581 | +1.158；[−0.368, +2.636] | 34/239/27 |
| E5 512 − E5 256 | RRF+多语 rerank | 0.66672 → 0.66440 | −0.232；[−1.054, +0.274] | 8/286/6 |
| MiniLM256 − E5 256 | dense | 0.65495 → 0.34737 | −30.758；[−35.551, −25.717] | 22/108/170 |
| MiniLM256 − E5 256 | RRF | 0.68423 → 0.53854 | −14.569；[−18.074, −11.097] | 34/149/117 |
| MiniLM256 − E5 256 | RRF+多语 rerank | 0.66672 → 0.67260 | +0.588；[−0.143, +1.350] | 21/270/9 |

这组新增证据适合讲四个有边界的发现：

1. **更少截断伴随 dense 均值改善，但不是每题改善。** E5 的语料截断从 4,240/5,183（81.81%）降至 731/5,183（14.10%）；dense nDCG 上升 2.204 pp。`742` 的正例 `32159283` 从 top-10 外升至第 1，而 `1137` 的正例 `33370` 从第 1 降至第 8，二者的候选 Recall 都保持 1。只能说长度变更后的排序有正有负，不能在没有证据位置分析时断定改善都来自保留尾部事实；256/512 是编码器输入截断，不是 chunking。
2. **上游改善未必保留到重排后的最终结果。** E5 的 dense 均值上升，但 RRF+rerank 的跨长度差值为 −0.232 pp、CI 跨 0。`1088` 在两种长度下候选 Recall 都为 1，但固定 50 的重排池 Recall 从 1 降到 0，正例由最终第 1 跌出 top-10。该案例定位到池截断前排序变化造成的覆盖损失；reranker 输入长度始终为 512，不能解释为“更长 reranker 看了更多内容”。RRF 的 Recall@10 还下降 1.000 pp，而 nDCG 均值上升，说明指标维度也可能出现取舍。
3. **替换 embedding 会改变混合路径的表现，不能只看名称或模型体积。** MiniLM/256 的 dense 均值比 E5/256 低 30.758 pp，RRF 差距为 14.569 pp；其 RRF 相对同一 lexical 基线反而为 −13.149 pp（CI [−16.859, −9.506]，39/150/111）。这反驳“混合一定优于词法”的无条件表述。这里比较完整模型方案，训练目标、训练数据、tokenizer、前缀与结构等因素同时不同，不能当作纯模型大小消融，更不能泛化到中文。
4. **同一个 reranker 的收益依赖上游。** 多语 rerank 在 MiniLM/256 的 RRF 上增加 13.407 pp（CI [+9.151, +17.651]，116/144/40），在 E5/256 上却是 −1.750 pp。两条最终 RRF+rerank 路径之间只差 +0.588 pp，270/300 题的 nDCG 相同、CI 跨 0；这不是通过等效性检验证明两模型等效。两组上游候选及池内容会变化，虽然 reranker 模型与预算固定，也不能把所有差值归为 reranker 单独的因果效果。反例 `715` 的候选 Recall 均为 1，换成 MiniLM 后重排池 Recall 1→0，正例 `18421962` 由第 7 跌出 top-10。

**第四组补充（已统一核验）：**MiniLM 从 256 延长到 512 后，语料截断率虽从 81.27% 降至 13.74%，dense nDCG@10 却从 0.34737 降至 0.19639，差值 **−15.098 pp**、95% CI [−18.654, −11.561]、W/T/L=34/164/102；这与 E5 的长度反应方向不同，不能把“减少截断”等同于“质量必然提升”。同样的 MiniLM 长度变化在 RRF+多语 rerank 下为 **+0.913 pp**、95% CI [−0.179, +1.904]、26/270/4；区间跨 0，模型对长度的适应与上游候选变化仍需进一步诊断，不能归因于 reranker 变长，因为它始终固定 512。

**进一步排查“为什么”：**[只读缓存诊断](evaluation/PUBLIC_GPU_LENGTH_DIAGNOSTIC.json)比较同一批已计算向量，没有新跑 GPU。MiniLM 的 336 个查询（含规则变体）在两种长度下最小 cosine 约为 1，最大坐标差约 `1.02e-7`；971 篇未超过 256 token 的文档也几乎不变。仅 padding 变长未见明显异常，而加入更多正文的 257～512 token 文档、超过 512 token 文档，其向量 cosine 均值分别约为 0.887、0.760。这个对照使明显 padding/mask 实现错误缺少支持，说明新增内容改变了表示；它不能单独证明语义稀释、训练分布或任何一种具体机制导致指标下降。

模型使用边界同样要说清：原始 SentenceTransformer 的[默认配置是 128](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2/blob/e8f8c211226b894fcb81acc59f3b34ba3efd5f42/sentence_bert_config.json)，固定 Xenova [结构上限为 512](https://huggingface.co/Xenova/paraphrase-multilingual-MiniLM-L12-v2/resolve/2c4055b12046f11709e9df2c122e59ffbdc2f900/config.json)。本次按登记矩阵显式使用 256/512，尚未评估官方默认 128；所以这不是默认 pipeline 的成绩，也不能把默认 128 说成已确认的训练长度。后续要验证长度适应假设，需要单独登记 128 基线或控制新增证据/干扰文本，而不是事后修改本轮已测参数。

以上区间未经多重比较校正；当前按 query ID 分别重采样，未校正不同问题之间可能存在的主题相关性。逐题案例按较大变化挑选，不能当作发生率。本专题的前三个 job 共 16,200 条观测；加上已完成的 MiniLM/512，SciFact 的 21,600 条观测仍只覆盖同一批 **300 个英文科学问题**。新增 FiQA 结果独立分析，中文 T2 尚无完整结果。共享 GPU、跨日中断与缓存复用也限制耗时比较，不能把恢复后完成得更快写成某个模型更快。

这组可以讲四项具体发现：

1. **融合既要看候选覆盖，也要看如何排序。** lexical、dense、RRF 的平均候选 Recall 分别为 0.51958、0.65419、0.71253；RRF 相对 lexical 的均值改善伴随更多正例覆盖。与此同时，normalized 与 RRF 的候选 Recall 相同，RRF 的 nDCG 仍高 3.539 pp，说明最终融合排序也值得单独比较；不能把这全部说成“找回了更多文档”。
2. **多语重排在本组均值为正，严重退化依然存在。** `1074` 的正例 `443960` 从 top-10 外升到第 1；`932` 的两个正例 `387010`、`48722` 从第 1/2 全部跌出 top-10。两题候选 Recall 和重排池 Recall 都为 1，后者不能解释成未进入重排池；总体仍有 157 题退化，不能只展示一个成功案例。
3. **扩大池子能补覆盖，却可能降低最终质量。** 重排池 50→100 的平均 Recall 从 0.60316 升至 0.65100，nDCG 均值却下降 0.736 pp。`10039` 的正例 `67785` 从池外进入池内并达到最终第 2；反例 `2587` 的正例 `89326` 始终在池内，却从最终第 1 降到第 4。这些证据分别定位覆盖增加与排序退化，不能将“更大池”直接视为优化完成。
4. **小幅均值变化需要结合触发率与区间。** 规则 rewrite 仅在 23/648 题触发（3.55%），最终 nDCG 为 3 改善、642 持平、3 退化，+0.032 pp 的 CI 跨 0，不支持明确普遍收益。英语 reranker 相对多语模型的差值也跨 0，不能因为它在 SciFact 某组均值较高就视为通用赢家；SciFact 与 FiQA 都是英文，数据集间差异不能归因于语言。

FiQA 文档编码有 **12,230/57,638=21.22%** 被 256-token 上限截断；后续完成的 E5/512 对照见下一节，不能直接套用 SciFact 的长度结论。官方 38 个空文档及指向空文档的 1 条选定测试正例均保留；未标注文档按零相关性计分不代表它们在现实中无关。该组仍只有检索质量证据，没有生成正确率、忠实度或在线延迟结论；CI 未做多重比较校正，极端案例不代表发生率。SciFact 300 题与 FiQA 648 题合计 948 个唯一问题，只汇总完成数量，不把两个数据集的相关性均值混成一个效果结论。

### FiQA 三组对照：减少截断和增加重排是否补回差距

新增 E5-small/512 于 22:32:16、MiniLM/256 于 22:50:31 完成；与 FiQA 首组的 corpus、query 和运行指纹一致。三组各自含 648 同题×18 配置一次观测，合计 34,992 条观测，独立 query 数仍为 648。以下为固定配置下的逐题配对差，2,000 次 bootstrap、seed=20261015；reranker 始终固定同一模型、512 输入上限及对应池预算。

| 同题对照（候选 − 参考） | 固定检索配置 | nDCG@10 参考 → 候选 | Δ pp；95% CI pp | W/T/L |
|---|---|---|---|---|
| E5 512 − E5 256 | dense | 0.33946 → 0.33298 | −0.649；[−1.677, +0.384] | 94/465/89 |
| E5 512 − E5 256 | RRF | 0.34399 → 0.34154 | −0.245；[−0.950, +0.427] | 93/460/95 |
| E5 512 − E5 256 | RRF+多语 rerank | 0.36991 → 0.37319 | +0.328；[−0.143, +0.750] | 49/564/35 |
| MiniLM256 − E5 256 | dense | 0.33946 → 0.13714 | −20.232；[−22.749, −17.949] | 48/274/326 |
| MiniLM256 − E5 256 | RRF | 0.34399 → 0.20613 | −13.785；[−15.648, −11.916] | 58/284/306 |
| MiniLM256 − E5 256 | RRF+多语 rerank | 0.36991 → 0.33909 | −3.082；[−4.232, −1.940] | 93/439/116 |

1. **E5 更少截断未产生明确的质量收益。** 512 下截断文档为 2,825/57,638（4.90%），相较 256 的 21.22% 明显减少，但 dense、RRF、RRF+rerank 的跨长度区间均跨 0。dense 有 94 题改善、89 题退化而平均差仍为负，说明 W/L 的数量不能替代差值幅度。`7448` 的正例 `418150` 从 dense top-10 外升到第 1；`11088` 的正例 `437100` 则从第 1 跌出 top-10，两题候选 Recall 均保持 1。
2. **输入更长也会改变候选与池覆盖。** E5 的 RRF+rerank 均值小幅上升，但 `9381` 的候选和池 Recall 都从 1 降至 0.5，原第 1 的正例 `384983` 不再出现在 top-10，另一个正例 `408123` 从第 5 到第 4。不能仅凭总体少截断就说每题保留了更多有效证据；这是编码器截断对照，不是 chunking，也不是 reranker 长度消融。
3. **较弱上游获得更大重排增益，不等于已追平较强路径。** MiniLM/256 自身的 RRF+rerank 相对 RRF 提高 **13.296 pp**（CI [+11.221, +15.344]，288/289/71），但其最终 RRF+rerank 相对 E5/256 仍为 **−3.082 pp**。两路径平均重排池 Recall 分别为 0.48642 与 0.60316，表明候选入口仍有差异；不能把单组件的大增益直接当成整个系统更优。
4. **保留模型替换后的覆盖反例。** 在 RRF+rerank 下，`3014` 的候选和池 Recall 从 1 降到 0，正例 `273282`、`341399` 从第 1/2 全部跌出 top-10，重排无法补回池外正例。反方向案例 `10039` 的池 Recall 从 0 升至 1，正例 `67785` 达到第 2。模型替换的总体负差值没有抹去局部改善，局部改善也不能否认整体差距。

MiniLM 与 E5 的比较涉及训练目标/数据、tokenizer、前缀和结构等多因素，不是纯参数规模实验；MiniLM 的官方默认 128 与本轮显式 256/512 的边界仍适用。上述 CI 未做多重比较或跨题主题相关性校正，极端案例不代表发生率。FiQA 和 SciFact 都是英文，不能把两者对长度或重排的不同反应归因于语言；效果按数据集分别报告。FiQA/MiniLM512 尚未完成，中文 T2 仍无完整结果，共享 GPU 和缓存复用也不支持独占速度结论。

## 4. 二十个项目追问与可辩护回答

### 1）你做的到底是什么，RAG 闭环到哪一步？

**回答：**项目是内部文档 Retrieval Hub 加策略 Dashboard。已做文档接入、索引、搜索、fetch、来源/新鲜度策略、HTTP/MCP 共用后端，并为检索阶段补可复现消融。当前测量主要回答“能否找到并排好证据”，没有把“能返回文档”包装成“生成答案正确”。原始 RAG 方法将检索与生成结合，这也说明仅有 retrieval 指标不能覆盖生成部分。[RAG 原论文](https://arxiv.org/abs/2005.11401)

**展示：**[架构图](ARCHITECTURE.md)、一个固定问题的 search→fetch→证据定位。追问“加生成器要测什么”时，回答第 16 题的四类结果，而不是只演示一条成功回答。

### 2）为什么 HTTP、MCP、Dashboard 要共用同一个后端？

**回答：**否则同一个 query 在不同入口可能用不同 ranking 或策略。这里 Dashboard 只呈现后端结果，不重新算 score；修改策略必须携带最近读取的 `expected_version`，遇到 409 不能静默覆盖；搜索返回的 `policy_version` 进入界面和评测记录。这个版本链可以解释“我改了权重，下一次查询为什么变化”。

**展示：**[契约说明](contracts/README.md)与[本地验收](evaluation/POSTGRES_MCP_ACCEPTANCE.md)。云端连接验收和本地 stdio 验收分开回答。

### 3）为什么同时保留 lexical 和 dense？是不是 embedding 一定更好？

**回答：**词法路径对精确名称、编号和术语匹配有价值；dense 用学习到的表示处理部分表达差异，但会受模型、领域、截断和索引覆盖影响。是否互补要看同一题集的候选覆盖与错误重合。历史真实库只有 6.742% passage 向量覆盖，dense Recall@10=0.2375 不能独立说明模型质量。公开矩阵使用完整 corpus 编码，正是为了去掉这项覆盖混淆。

**追问准备：**当前 SQLite 是 FTS5 BM25；历史 PostgreSQL lexical 是 `ts_rank`，不是 BM25。公开 runner 复用生产词项处理并使用 SQLite FTS5，不宣称它重跑了同一 PostgreSQL 引擎。

### 4）embedding 的输入、池化和相似度有什么容易做错的地方？

**回答：**先固定模型 revision、tokenizer、前缀、长度、pooling 和归一化。E5 对 query/passage 的前缀有要求，中文也要遵守；padding 位置不能参与 mean pooling。当前实现按 attention mask 平均、L2 归一化，再比较点积；对单位向量点积等于 cosine。E5 官方卡给出了这些输入与池化约定。[E5 模型卡](https://huggingface.co/intfloat/multilingual-e5-small)

**展示：**[`gpu_onnx.py`](../backend/benchmarks/gpu_onnx.py) 的 `mean_pool_normalize` 与[模型配置](../backend/samples/rag_ablation/public_models.json)。分数不是概率；相似度大于某值不能直接当作“答案置信度”。

### 5）为什么用 RRF？k=60 有什么意义？

**回答：**RRF 按各路排名相加：`sum(1 / (k + rank))`，未出现在某路的文档不给该路贡献。它降低了对不同打分尺度可比性的要求，但也丢掉原始分数间距。k 越大，头部相邻名次的相对差异越小；60 是当前配置，不是证明最优的常数。公开矩阵预设 10/60/100 对照；首组 k=10 比 60 高 1.842 pp，39/243/18，并不证明跨数据集最优。[RRF 原论文](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf)

**项目证据：**历史真实库 RRF 比 normalized hybrid 的 nDCG@10 高 4.242 pp，但比 lexical 低 13.984 pp。可以说改善了某种融合方式，不能说战胜所有基线。

### 6）reranker 能补回没有召回的文档吗？怎样定位瓶颈？

**回答：**在固定候选池里重排不能召回池外文档。先查 relevant document 是否进入候选池，再查候选截断、最终排序与返回 k。候选池扩大可能提高可达到的相关性上限，也会增加重排工作量和干扰项；效果必须实测。CrossEncoder 对 query-document 联合编码，适合对候选集合精排，成本也随待评分配对增加。[Sentence Transformers 官方检索与重排说明](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

**展示：**公开矩阵的 candidate 25/50/100/200 和 rerank pool 20/50/100。它们是两个不同截断；不能把候选池变化全部归因于模型。

**实测追问：**SciFact `1088` 在重排池 50 中可从 top-10 外升到第 1，但缩池到 20 后正例没有进入重排池；`1303` 的正例始终在 50 池内却从第 1 跌出 top-10。这两种失败需要不同排查路径。

### 7）历史 rerank 为什么没有总体提升？

**回答：**先陈述事实：nDCG@10 总体 −0.401 pp，英文题组上升，中文题组下降。可能因素包括英语 MS MARCO 训练的适配、证据位置被截断、代表 passage 选择、候选池截断和不完整 qrels。这些是待验证假设；没有真实库逐题记录，不能给每个退化问题编原因。

**验证设计：**固定同一题集、同一候选与池大小，比英语与多语 reranker；再查看正例重排前后位置和实际送入模型的文本。中英文题目主题不相同，所以这里没有识别出“语言本身”的因果影响。

### 8）query rewrite 的收益怎么独立测？

**回答：**现有 rewrite 是固定双语规则，包含原 query 与有限扩展，不是 LLM 生成。应先记录触发率，再做 RRF、RRF+rewrite、RRF+rerank、RRF+rewrite+rerank 四格对照。交互项为 `both − rewrite_only − rerank_only + neither`；正交互只表示 nDCG 尺度上超加性，不保证 both 相对基线一定为正。

**展示：**[`rag_ablation.py`](../backend/src/research_agent/rag_ablation.py) 的 interaction 计算。历史六阶段缺 rewrite-only；首组公开四格已测得 rewrite 在 RRF 上 +0.393 pp，和多语 rerank 组合后的增量约 +0.001 pp，交互为 −0.392 pp。规则不触发的 query 也留在总体分母；该组触发率 12%，不能只保留改善题。

### 9）Recall、MRR、nDCG 为什么都要报？能手算吗？

**回答：**Recall 看找回多少已标正例；MRR 看第一个正例出现多早；nDCG 同时考虑等级和位置。一个简单例子：A 的 grade=2、B 的 grade=1，返回 `[不相关, B, A]`。Recall@3=1，MRR@3=1/2；DCG@3=`1/log2(3)+3/log2(4)`，IDCG@3=`3+1/log2(3)`，nDCG@3≈0.587。用 gain=`2^grade−1`，公式和实现必须一致。

**边界：**按唯一 document ID 计数；无正 qrels 的控制题不混入相关性平均；未标注文档在当前记分中按 0，但这不等于现实中不相关。指标上升也不直接等于答案正确率上升。

### 10）五次重复为什么不是五倍样本量？CI 跨 0 怎么解释？

**回答：**同一问题重复执行主要增加运行稳定性观察，不增加独立相关性问题。先在每个问题内平均重复，再对同一 query 的配置差做配对重采样；有主题 cluster 时以 cluster 为单位。本次 SQLite 相关性样本是 16 题，不是 1,700 题。CI 跨 0 表示在这个重采样方案下方向不稳定；不跨 0 也不能消除选题偏差、标注偏差或多重比较问题。

**项目边界：**真实库匿名 JSON 只有聚合结果，不能从均值和轮数还原逐题 CI。所有比较目前作探索性描述，没有据此声称统计显著或总体泛化。

### 11）怎么防止评测泄漏和只测容易题？

**回答：**锁定官方 revision 和 qrels，先于检索固定问题集合，不按分数挑题；保留完整 corpus，不能只取相关文档。FiQA/SciFact 用官方 test，train/dev query ID 不得交叉；T2 公开版本只有 dev，必须如实称 dev 评测，1,000 题按固定 seed 的 hash 顺序选择。参数若根据 test 结果调整，就不能再把它叫未经选择的 test 结论。

**剩余风险：**这些措施防止本项目的数据处理和选题泄漏，不能证明预训练模型没见过公开基准。还需要记录模型训练数据关系，并用独立领域/时间留出样本补证。[BEIR 原论文](https://arxiv.org/abs/2104.08663)、[本项目加载器](../backend/benchmarks/public_benchmark_data.py)

### 12）256/512 tokens 是 chunk size 消融吗？

**回答：**当前公开 runner 是每篇文档的 title+text 被 encoder 截断到 256 或 512，仍然是一文档一向量；reranker 配对长度另固定为 512。这是输入截断对照，不是把长文切成多个 chunk。真正 chunking 对照应改变切分边界/overlap，同时固定 parent document qrels 与聚合去重规则，记录页码和 offset。

**解释“为什么”：**更多输入可能保留尾部证据，也可能增加无关内容和成本。生成器能接受更长上下文，也不代表能同样利用所有位置；相关研究给出了位置敏感性的实验，但本项目还没测生成器的这种现象。[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)

### 13）你用了向量检索，为什么还不能说用了 HNSW？

**回答：**当前公开 runner 对 GPU 编码得到的全部 vectors 在 CPU 做 exact dot-product scan，并稳定处理 top-k 并列；它是精确参照，没有 HNSW 索引。HNSW 是近似搜索的另一层取舍。后续需固定 vectors 与距离，测 ANN top-k 与 exact top-k 的重合率，同时单独报 qrel relevance、内存和查询成本。pgvector 官方也明确区分 exact 与 approximate 搜索。[pgvector 文档](https://github.com/pgvector/pgvector#indexing)

**现场准备：**能解释 exact 扫描约 O(Nd)，以及 top-k 的堆/partition 选择；不要把“精确近邻召回 100%”误说成“相关文档召回 100%”。

### 14）metadata filter、来源权重和权限是同一回事吗？

**回答：**filter 决定哪些内容允许进入本次结果；来源权重影响合法候选里的排序。租户 ACL 应来自可信身份与服务端授权，不应由普通 query 参数自行决定。当前项目有过滤、禁用来源与 read/admin 边界，但没有生产企业 ACL 的完整证据。越权控制必须覆盖候选、重排输入、fetch、引用和缓存，不能只隐藏 UI 条目。

**ANN 追问：**近似索引加 filter 可能返回不足 k；应检查执行计划、过滤选择性与搜索预算。pgvector 的文档说明近似索引过滤和 iterative scan 的行为，这需要版本对应的测试，不能套用本项目 exact 路径的结论。[pgvector filtering](https://github.com/pgvector/pgvector#filtering)

### 15）关闭一个组件后指标不变，是否应该删掉它？

**回答：**先查组件是否触发、是否改变候选、是否只影响低于评估截止位的结果，以及样本是否覆盖它的目标场景。当前关闭 concept expansion 或 title guard 的 nDCG@5 都没变，但 title guard 关闭后平均 payload 从约 1420 字节变为 2277 字节。排序指标没变不等于行为没变，也不等于组件有已证明的收益。

**下一步：**增加预先设计的规则触发和歧义反例，分别报告总体与触发切片；不根据某次结果临时改题再称验证成功。

### 16）能正确返回空结果，是否证明会拒答、不会幻觉？

**回答：**不能。当前四个 SQLite 控制是“不可能过滤条件”，只验证过滤与空返回。检索失败、语料确实无答案、用户问题歧义、证据冲突是不同情形。生成评测应分别看答案正确性、陈述是否被证据支持、引用是否对应、该答/该拒的错误率；同时构造无证据、干扰证据、冲突证据与有证据场景。

**反例：**一段话忠实复述了错误或过期来源，可以“忠实”但不正确；答案碰巧正确却没有被提供证据支持，也不能说引用可靠。当前仓库尚无这组生成实测，不能填写幻觉率下降数字。

### 17）文档中出现“忽略规则、泄露凭据”怎么办？引用怎样可信？

**回答：**入库文本、snippet、正文都是不可信数据。UI 按纯文本渲染；未来生成器需要把证据作为资料边界，不把其中指令当作权限。工具权限和租户隔离由服务端控制，不能靠 prompt 替代。引用要保留稳定文档 ID、版本、页码/offset 与实际使用 passage，让用户能回到支持该陈述的原文位置。

**现有与待补：**当前契约支持 fetch 原文和本地引用验收；生产级注入攻击集、撤权传播、逐陈述引用正确率还需实测。全文 fetch 不可静默截断；若增加 passage fetch，应走契约变更与跨入口验收。

### 18）3060 Ti 跑起来之后，怎样证明用了 GPU，性能怎么讲？

**回答：**“可用 provider 列表有 GPU”不是执行证据。当前实现要求 ONNX profile 中实际 Node kernel 使用 DML，并记录模型图/tokenizer 哈希、runtime、adapter 等信息；仍可能有 CPU 算子。需要同时看设备与资源 telemetry，不能把 host profile duration 当纯 GPU kernel 时长。

**计时边界：**公开矩阵缓存真实的 query vectors、召回候选和 pair scores，便于比较质量；它的 pipeline p50/p95 是缓存辅助回放。真实推理 telemetry 另记，但不能简单把不同批次的统计值相加当在线 p95。当前 dense scan 是 CPU exact，GPU 负责 encoder/reranker。线上成本要另测实际 tokenizer 数、推理/网络/等待、并发、峰值显存与缓存条件。

累计推理快照只覆盖同一检查点中已经记录的调用，截止于对应完整 job 保存时。它不包含另行归档的失败运行、未落盘的原生失败调用、pilot、模型重载，以及快照后的进行中工作；不能把调用耗时之和称作整个 campaign 总成本或墙钟时长。报告会保留快照时间和统计范围，恢复前后的累计快照也不能相加。

**共享 GPU 限制：**10月16日恢复时仍有其他训练与推理任务使用同一张显卡。全设备利用率和显存不能全部归为本项目；墙钟耗时、吞吐和剩余时间估计会受资源争用影响，不能写成独占 GPU 基准或模型本身的速度提升。恢复前约 4,472 MiB 可用显存只是一时快照，不是持续资源保证。

### 19）两天实验中断、数据更新或模型变了怎么办？

**回答：**用唯一 query/配置记录和事务 checkpoint，只将成功且无降级的结果标完成；中断后校验数据、qrels、模型、源码和配置指纹，继续缺失项。失败尝试单独保留，不能从报告里消失。停止预算是 incomplete 状态，不是完成。模型变更后不能直接复用旧 embedding 或旧 pair scores。

**本次恢复证据：**第一次恢复核对指纹一致、SQLite `quick_check=ok` 和 5,400 条观测保留，20:06 跳过首组继续后续任务；随后保存 E5/512 和 MiniLM/256，共 16,200 条观测。MiniLM/512 再次原生退出后，9 个冻结源码哈希和数据库检查仍通过。21:05:48 的旧锁安全门阻止启动，确认旧 writer 已退出后才备份并移除失效锁；21:06:19 重启监督器，21:07:19 正式恢复，21:07:27 MiniLM/512 编码达到 320/5,183。之后以 21:12:56 的完整 summary 确认第四组完成，累计 21,600 条观测，继而进入 FiQA 编码；没有将编码进度提前记为完成。恢复成功仍不证明原生崩溃根因已解决。原截止仍为 **10月17日 16:10:19**，停机未延长预算。

**第三次中断：**21:44:51 FiQA/256 保存后，21:44:53 原生退出；五组完整结果共 33,264 条观测保留，9 个冻结哈希和 `quick_check` 仍通过。22:11:15 同配置重启监督器，22:12:15 正式恢复并跳过五组，22:13:13 FiQA/512 编码为 3,216/57,638。当时故障前设备快照为 4,304/8,192 MiB，不能说显存已满，更不能把这作为 OOM 的证明；该时刻第六组尚未完成，预算没有重置。

**第四次中断与恢复：**FiQA/E5-small512 于 22:32:16 完成、MiniLM256 于 22:50:31 完成，22:50:33 再次原生退出；此时七组共 56,592 条观测、9 个冻结哈希和 `quick_check` 全部核验通过。23:09:03 同配置启动监督器、23:10:03 正式恢复并跳过七组，23:10:16 FiQA/MiniLM512 编码达到 520/57,638。故障前显存快照为 4,299/8,192 MiB，同样不足以证明 OOM；第八组没有被提前记为完成，原截止仍为10月17日16:10:19。

**生产延伸：**策略更新、源文件更新和 embedding 模型更新是不同版本维度。缓存键必须体现影响输出的版本；增量索引要能幂等重试、删除与回滚。当前实验恢复机制可以展示，生产全链增量一致性需单独做故障演练。

### 20）如果要求现场写代码和讲一个失败，你准备展示什么？

**回答：**代码可从“去重并稳定返回 top-k”“手算并实现 nDCG”“按 query 聚合重复后计算配对差”“缓存键防止模型版本混用”中选一项，说明复杂度并覆盖空输入、重复 ID、并列、k 超范围、NaN、缺失 qrels。应能解释自己使用的 Python/SQL，而不只打开最终报告。

**失败复盘：**可讲历史 rerank 没带来总体收益：先看到总体几乎持平，再切语言组发现方向相反；承认旧报告无逐题证据，补同候选多语重排与四格消融，保留负结果。另一例是来源权重 ×10 仅让 1/16 题改善，因而没有把它直接设为“最优策略”。按“问题—假设—实现—结果—限制—下一步”组织，说明本人实际贡献。

> 为文档检索 Hub 补充可复现消融评测：在固定虚构样例上执行 17 个配置、1,700 次生产搜索调用，按独立 query 统计 Recall/MRR/nDCG、配对 bootstrap 与逐题退化；验证策略版本、来源及 metadata 过滤，记录延迟边界和 payload。

> 复核 PostgreSQL lexical/dense/fusion/rerank/rewrite 历史结果，定位向量覆盖不足、分语言结果方向不同和不完整实验设计；实现固定公开数据/模型 revision、完整语料、预锁定问题及可恢复 GPU 实验流程。

七组公开报告已经统一核验；效果数值仍需明确对应的数据集、模型、长度和检索配置，可增加一条限定范围的表达：

> 在 SciFact 300 题和 FiQA 648 题的官方 test 上，保留各自完整语料，完成七组各 18 配置的公开检索消融，累计 126 配置单元、56,592 条观测、948 个唯一问题；按数据集报告配对 bootstrap、W/T/L 与正负样例，在 FiQA/E5-small/256 中观察 RRF 相对 lexical 的 nDCG@10 +11.233 pp，同时揭示减少截断不保证提升、重排不能完全补回上游差距等边界；通过同指纹检查点恢复保留已完成结果，完整中英矩阵仍待完成。

这个模板不把单一数据集的结果写成生产收益或全矩阵结论。不要把原报告日期改成自己的新实测日期，也不要写“幻觉率降低”“生产 p95 降低”或“最优模型”而没有对应证据。

面试前建议完成一次 30 分钟自测：5 分钟画请求和数据链路，10 分钟手写一个指标/排序/缓存函数并测试，10 分钟复盘一正一负结果，5 分钟解释生成、ANN、权限和成本四个尚未闭合的边界。能清楚说出下一项实验如何区分两种解释，比堆砌组件名称更能展示这个项目的工作深度。
